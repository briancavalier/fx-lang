# Phase 2.5 learnings

Date: 2026-06-06

## Purpose

implementation plan in `notes/2026-05-23-implementation-phases.md`.

Use it for decisions, surprises, rejected approaches, and implications for
later phases. Keep entries short, concrete, and tied to the implementation

## Entries

- Decision: Keep Phase 2.5 executable fixtures as expected-passing checker
  inputs from the start.
- Context: Phase 2.5 starts after Phase 1 and Phase 2 parser/checker support
  for the pure fixture surface has landed, so `examples/phase-2.5/` should give
  later compiler work checked inputs instead of unsupported goal targets.
- Applies to phase(s): Phase 2.5.
- Future implication: Compiler IR, lowering, JavaScript codegen, and runtime
  tests can assume these fixtures parse and check before code generation starts.
- Revisit when: A future executable fixture needs accepted syntax or semantics
  that the checker does not yet support.

- Decision: Keep backend compiler code in a separate `fx-compiler` crate and
  use `fx-core::Analysis` as the handoff from front-end validation.
- Context: `fx-core::Analysis` already owns the indexed module graph, resolver
  output, checker output, and diagnostics grouped by path. A separate compiler
  crate lets backend work depend on those facts without adding executable
  backend concerns to `fx-core` or `fx-lsp`.
- Applies to phase(s): Phase 2.5.
- Future implication: Core IR, lowering, and JavaScript codegen should build on
  `fx-compiler::CompileSession` after `prepare_compile` rejects existing
  diagnostics.
- Revisit when: Compiler phases need lower-level checker internals that are not
  exposed through `Analysis`.

- Decision: Make the initial core IR typed, source-spanned, and free of
  row-polymorphic tail details.
- Context: Work Item 3 defines representation types only. Carrying
  `fx_core::Type` and `fx_syntax::span::Span` keeps later lowering and
  diagnostics connected to existing checker facts, while record and variant
  type declarations retain only concrete runtime shape metadata.
- Applies to phase(s): Phase 2.5.
- Future implication: Lowering should erase open-row source machinery before
  backend codegen, and backend work can use `TailPosition` markers without
  implementing tail-call optimization yet.
- Revisit when: JavaScript codegen or effect lowering needs a smaller backend
  type model than `fx_core::Type`.

- Decision: Lower checked modules into core IR only after `prepare_compile`
  has accepted the workspace.
- Context: Work Item 4 adds `lower_to_core`, which consumes
  `fx-compiler::CompileSession` and reuses `fx-core::Analysis` for module
  order, resolved global references, checked top-level types, and source spans.
  It reports compiler diagnostics only for accepted-but-not-yet-executable
  constructs such as tuple type declarations.
- Applies to phase(s): Phase 2.5.
- Future implication: JavaScript codegen can start from `CoreProgram` and does
  not need to rerun parser, resolver, or checker work.
- Revisit when: Lowering needs richer exact expression types than the current
  typed-span/display fallback can provide.

- Decision: Keep the JavaScript runtime helpers under a frozen `__fx`
  namespace.
- Context: Work Item 5 adds direct Node-tested helpers for variant construction,
  variant matching, list inspection, list tails, and primitive equality without
  generating JavaScript from core IR yet.
- Applies to phase(s): Phase 2.5.
- Future implication: JavaScript emission should reference `__fx.*` helpers
  instead of generating helper names that could collide with user declarations.
- Revisit when: Module packaging decides whether the runtime is emitted inline,
  imported, or bundled.

- Decision: Emit deterministic JavaScript module shells before expression
  codegen.
- Context: Work Item 6 adds ESM module emission, generated user-name mangling
  with a `__fx_user_` prefix, import namespaces with a `__fx_import_` prefix,
  and explicit throwing value stubs until expression codegen lands.
- Applies to phase(s): Phase 2.5.
- Future implication: Work Item 7 should replace value stubs with expression
  bodies while preserving the same module paths, import format, and name
  isolation.
- Revisit when: Packaging decides whether generated modules should be emitted as
  ESM files, bundled text, or another module format.

- Decision: Generate pure JavaScript expressions directly from core IR in
  expression position.
- Context: Work Item 7 replaces module-shell stubs with JavaScript for
  literals, locals, let bindings, functions, lambdas, calls, recursion, records,
  record updates, lists, variants, matches, and binary operators. Match
  expressions use generated IIFEs so pattern tests and bindings remain local to
  the expression being compiled.
- Applies to phase(s): Phase 2.5.
- Future implication: CLI and smoke-test work can execute generated ESM modules
  through Node without adding another intermediate codegen layer.
- Revisit when: Tail-call implementation, source maps, or optimized statement
  emission becomes necessary.
