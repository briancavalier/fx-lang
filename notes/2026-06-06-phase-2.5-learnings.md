## Entries

- Decision: Keep Phase 2.5 executable fixtures as expected-passing checker
  inputs from the start.
- Context: Phase 2.5 starts after Phase 1 and Phase 2 parser/checker support
  for the pure fixture surface has landed, so `examples/phase-2.5/` should give
  later compiler work checked inputs instead of unsupported goal targets.
- Applies to phase(s): Phase 2.5.
- Future implication: Compiler IR, lowering, JavaScript codegen, and runtime
  tests can assume these fixtures parse and check before code generation starts.
- Revisit when: A future executable fixture needs accepted syntax or semantics
  that the checker does not yet support.

- Decision: Keep backend compiler code in a separate `fx-compiler` crate and
  use `fx-core::Analysis` as the handoff from front-end validation.
- Context: `fx-core::Analysis` already owns the indexed module graph, resolver
  output, checker output, and diagnostics grouped by path. A separate compiler
  crate lets backend work depend on those facts without adding executable
  backend concerns to `fx-core` or `fx-lsp`.
- Applies to phase(s): Phase 2.5.
- Future implication: Core IR, lowering, and JavaScript codegen should build on
  `fx-compiler::CompileSession` after `prepare_compile` rejects existing
  diagnostics.
- Revisit when: Compiler phases need lower-level checker internals that are not
  exposed through `Analysis`.

- Decision: Make the initial core IR typed, source-spanned, and free of
  row-polymorphic tail details.
- Context: Work Item 3 defines representation types only. Carrying
  `fx_core::Type` and `fx_syntax::span::Span` keeps later lowering and
  diagnostics connected to existing checker facts, while record and variant
  type declarations retain only concrete runtime shape metadata.
- Applies to phase(s): Phase 2.5.
- Future implication: Lowering should erase open-row source machinery before
  backend codegen, and backend work can use `TailPosition` markers without
  implementing tail-call optimization yet.
- Revisit when: JavaScript codegen or effect lowering needs a smaller backend
  type model than `fx_core::Type`.
