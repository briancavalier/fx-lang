# Phase 2.5 work plan

Date: 2026-06-06

## Purpose

This note breaks Phase 2.5 from
`notes/2026-05-23-implementation-phases.md` into implementation units. Phase
2.5 should make the accepted pure Phase 1 and Phase 2 language executable by
adding a narrow compiler path, a desugared core IR, and a first JavaScript
backend.

This is a backend spike, not a production compiler. The goal is runnable output
for the already accepted pure language before effects introduce handler and
runtime design pressure.

## Scope

Include:

- a desugared core IR for checked pure modules;
- lowering from checked modules into the core IR;
- JavaScript code generation for Phase 1 and Phase 2 examples;
- a small JavaScript runtime for variants, pattern matching, lists, and required
  primitives;
- a CLI compile command such as `fx compile --target js`;
- runnable Node smoke tests for generated JavaScript;
- compact Phase 2.5 examples or acceptance programs.

Defer:

- effect declarations, effect rows, handlers, and resumptions;
- scoped effects and coeffects;
- C or native code generation;
- production packaging, bundling, source maps, and optimization;
- full standard-library design;
- advanced tail-call implementation beyond preserving tail-position information
  where practical and documenting current behavior.

## Work units

### 1. Phase 2.5 setup and executable fixtures

Create `examples/phase-2.5/` with compact pure programs that exercise runtime
behavior independently from parser and checker diagnostics.

The initial fixtures should cover:

- exported `main` values;
- records and record update;
- variants and matches;
- lists;
- functions and lambdas;
- recursion;
- imports across modules.

Create `notes/2026-06-06-phase-2.5-learnings.md` using the same entry shape as
the Phase 1 and Phase 2 learning logs.

Acceptance:

- Phase 2.5 examples are valid checker inputs before code generation starts.
- The learning log exists before backend representation decisions start
  accumulating.
- Unsupported runtime behavior is documented as an explicit later work item or
  deferment, not left implicit.

### 2. Compiler crate/module boundary

Decide where the compiler path lives. Start conservatively with a new compiler
module or crate that depends on `fx-core` analysis output instead of duplicating
parser or checker behavior.

The compiler entry point should accept already checked modules and return either
generated JavaScript or existing diagnostics.

Acceptance:

- Parser and checker diagnostics remain owned by the existing syntax/core paths.
- Code generation cannot run on an unchecked or failed module.
- The compiler boundary is testable without going through the CLI.

### 3. Core IR shape

Define a desugared core IR for the accepted pure language. The IR should be
small, typed enough for backend decisions, and explicit about constructs that
surface syntax currently hides.

The initial IR should represent:

- module imports and exports;
- literals;
- variables and bindings;
- functions, lambdas, and calls;
- records, field access, and record update;
- variant construction;
- match expressions;
- lists;
- tail-position markers where they are cheap to preserve.

Acceptance:

- The IR can represent every accepted Phase 1 example.
- The IR can represent the accepted Phase 2 row examples without preserving
  source-only row-polymorphism machinery.
- Pretty/debug output is available for focused lowering tests.

### 4. Lowering from checked AST to core IR

Lower checked modules into the core IR using resolved names and checker
semantics. Lowering should erase syntax conveniences while preserving enough
source spans for compiler diagnostics.

Acceptance:

- Lowering tests cover records, variants, matches, lists, functions, lambdas,
  recursion, and imports.
- Lowering rejects no program that `fx check` accepts within the Phase 2.5
  supported subset.
- Any unsupported accepted construct produces a compiler-specific diagnostic
  before JavaScript emission.

### 5. JavaScript runtime value representation

Add the smallest runtime needed by generated JavaScript.

The runtime should define:

- variant value construction and inspection;
- match dispatch helpers;
- list helpers required by accepted examples;
- equality or primitive helpers only where examples require them.

Acceptance:

- Runtime helpers have direct unit tests independent of generated code.
- Variant tags and payloads are stable enough for generated match code.
- Runtime helper names are isolated from user-generated names.

### 6. JavaScript name and module emission

Implement deterministic JavaScript emission for modules, imports, exports, and
user-defined names.

Start with a simple module format that Node can run in tests. Avoid bundling and
source-map work in this phase.

Acceptance:

- Generated names cannot collide with runtime helper names.
- Cross-module imports from Phase 1 and Phase 2 examples execute under Node.
- Output is deterministic enough for focused snapshot or golden tests where
  useful.

### 7. JavaScript expression and declaration codegen

Generate JavaScript for core declarations and expressions.

Cover:

- literals;
- local bindings;
- functions, lambdas, and calls;
- recursion;
- records and field access;
- record update;
- lists;
- variant construction;
- match expressions.

Acceptance:

- Generated JavaScript executes accepted Phase 1 examples under Node.
- Generated JavaScript executes accepted Phase 2 row examples under Node.
- Runtime behavior matches checker semantics for the supported pure subset.

### 8. CLI compile command

Add `fx compile --target js` with a minimal output contract.

The command should run parse/check first, reject diagnostics before emission,
and then write JavaScript to either stdout or an explicit output path. Choose one
default behavior and document it in the command help.

Acceptance:

- `fx check` behavior remains unchanged.
- `fx compile --target js` rejects programs with existing parser/checker
  diagnostics before writing output.
- Unknown targets produce a clear CLI diagnostic.
- The command can compile Phase 2.5 examples in a way Node smoke tests can
  execute.

### 9. Generated-code smoke tests

Add tests that compile fixture programs, execute the generated JavaScript with
Node, and compare observable results.

Keep these separate from parser, checker, and LSP tests so backend failures do
not obscure front-end diagnostics.

Acceptance:

- Smoke tests cover records, record update, variants, matches, lists, functions,
  lambdas, recursion, and imports.
- Tests execute generated JavaScript with Node and assert deterministic output.
- Test fixtures are compact and do not duplicate implementation logic as their
  oracle.

### 10. Diagnostics and unsupported-subset polish

Make compiler-specific diagnostics clear at the boundary between checked input
and supported executable output.

This work item should not redesign parser or checker diagnostics. It should only
cover errors introduced by the new compile path, such as unsupported accepted
constructs or backend target problems.

Acceptance:

- Parser/checker failures are still reported by the existing diagnostics path.
- Compiler diagnostics point to the source span that caused the unsupported
  lowering or emission case where possible.
- The learning log records every accepted-but-not-yet-executable construct.

### 11. Phase 2.5 acceptance sweep

Wire the supported examples into the normal validation path and run a final
compiler-focused sweep.

Final acceptance commands:

```sh
cargo fmt --all --check
cargo test --no-run
cargo check
node --version
cargo run -q -p fx-cli -- compile --target js examples/phase-2.5
```

Run direct Node smoke tests through the Rust test harness or a documented helper
command, depending on the implementation chosen above.

Acceptance:

- All Phase 1 and Phase 2 checker fixtures still pass.
- Phase 2.5 compile tests pass.
- Generated JavaScript runs under Node and produces expected observable values.
- Any environment-specific runtime-test blocker is documented with the exact
  command and failure mode.

## Suggested implementation order

1. Create executable fixtures and the Phase 2.5 learning log.
2. Establish the compiler crate/module boundary.
3. Define the core IR.
4. Lower checked modules into the core IR.
5. Add the JavaScript runtime representation.
6. Emit JavaScript names, modules, imports, and exports.
7. Emit JavaScript expressions and declarations.
8. Add the CLI compile command.
9. Add generated-code smoke tests.
10. Polish compiler diagnostics and unsupported-subset reporting.
11. Run the Phase 2.5 acceptance sweep.

## Notes for future phases

- Keep effect rows and handlers out of this compiler spike. Phase 3 can choose
  whether direct style, CPS, generators, or a runtime protocol fits the actual
  effect semantics.
- Preserve tail-position information in the core IR when cheap, but do not make
  tail-call optimization a Phase 2.5 requirement.
- Keep the JavaScript runtime small and explicit. A future standard library or
  packaging story should not be inferred from this spike.
