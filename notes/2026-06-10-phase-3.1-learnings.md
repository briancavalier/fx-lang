# Phase 3.1 learnings

Date: 2026-06-10

## Purpose

This note records implementation learnings and decisions from Phase 3.1 of the
implementation plan in `notes/2026-05-23-implementation-phases.md`.

Use it for runtime protocol decisions, executable subset boundaries, rejected
approaches, and verification evidence.

## Entries

- Decision: Represent effectful JavaScript regions as explicit runtime
  computations while preserving the direct JavaScript emitter for pure code.
- Context: Operation calls and handlers need a continuation for explicit
  `resume`, but pure Phase 1 through Phase 2.6 examples should keep their
  compact direct output. The runtime now provides `__fx.effect`, `__fx.pure`,
  `__fx.perform`, `__fx.bind`, `__fx.handle`, and `__fx.run`; the emitter uses
  the computation path only for operation/handler control or calls to
  effectful functions.
- Applies to phase(s): Phase 3.1.
- Future implication: Additional effectful expression forms should lower into
  the computation emitter instead of adding ad hoc `__fx.run` calls at each
  operation site.
- Revisit when: Multi-shot resumption laws, scoped effects, effect masking, or
  cleanup/resource behavior need a stronger semantic contract.

- Decision: Preserve checked local and global function types in core lowering
  so the JavaScript emitter can detect effectful helper calls.
- Context: Handler helper functions such as `catch` and `choose-first` return
  computations even when their callers are pure after handling the effect.
  Relying on display-type parsing lost function effect rows, which caused
  generated code to return computation objects or run operations outside their
  handlers. Lowering now uses checked symbol and local parameter types where
  available.
- Applies to phase(s): Phase 3.1.
- Future implication: Avoid using hover/display strings as semantic compiler
  input for effectful lowering. If more type precision is needed, carry checked
  types directly through lowering.
- Revisit when: The compiler IR grows a richer typed core or supports more
  effectful expression forms.

- Decision: Add executable smoke tests for handled `Raise` and resumptive
  `Choose` before expanding the supported subset.
- Context: `cargo test -p fx-compiler` now covers direct runtime helper
  behavior and generated Node execution for handled `Raise` returning `0` and
  `Choose` resuming with the left branch to produce `11`. `cargo test -p
  fx-cli` now expects `examples/phase-3` to compile with the effects runtime
  instead of rejecting all handlers with `unsupported-effect-runtime`.
- Applies to phase(s): Phase 3.1.
- Future implication: Keep extending generated Node smoke tests before
  broadening the runtime subset so unsupported accepted constructs do not
  silently emit incorrect JavaScript.
- Revisit when: Unsupported diagnostics are tightened for effect constructs
  outside the current executable subset.

- Decision: Preserve expression statements in block AST and lower them as
  explicit `Sequence` IR.
- Context: The parser previously accepted multiple expressions in a block but
  retained only the final result expression. That made `emit-twice`-style
  effect sequencing impossible to execute faithfully. Blocks now preserve
  earlier expressions as `Stmt::Expr`, the checker accumulates their effects,
  and the JavaScript emitter sequences effectful statements with `__fx.bind`.
  Generated Node smoke coverage proves two emitted operations run in order
  across a handler/resume boundary.
- Applies to phase(s): Phase 3.1 and later block-syntax work.
- Future implication: Future block forms should preserve source evaluation
  order in AST and IR rather than relying on parser-side discarded expressions.
- Revisit when: The language adds do-style sequencing or statement forms with
  more than discarded-value semantics.

- Decision: Reject accepted-but-not-executable effectful expression positions
  during lowering with `unsupported-effect-runtime`.
- Context: Phase 3 checking can accept effectful expressions in more positions
  than the first JavaScript computation emitter supports, such as effectful
  list items. Lowering now audits core expressions and reports compiler
  diagnostics for unsupported effectful positions before JavaScript emission.
  Supported positions include operation calls, handlers, effectful helper
  calls with pure arguments, lambdas as thunks, sequencing, `if` branches, and
  binary operands.
- Applies to phase(s): Phase 3.1.
- Future implication: New executable effect positions should move from the
  unsupported audit into the computation emitter with generated Node tests.
- Revisit when: Effectful records, lists, matches, call arguments, or other
  expression forms become Phase 3.1+ runtime targets.
