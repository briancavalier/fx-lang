# Phase 3.1 work plan

Date: 2026-06-10

## Purpose

This note breaks Phase 3.1 from
`notes/2026-05-23-implementation-phases.md` into implementation units. Phase
3.1 makes the ordinary Phase 3 effect subset executable through the existing
`fx compile --target js` path.

Phase 3 already accepts effect declarations, effect rows, operation calls,
handlers, explicit `resume`, and JavaScript runtime gating. This phase should
replace the `unsupported-effect-runtime` gate for a small supported subset
without reopening Phase 3 checker semantics.

## Evaluation of proposed direction

The proposed direction is right: start with a narrow runtime spike for
operation requests, handler dispatch, ordinary returns, and explicit `resume`,
then lower just enough of operation calls and `handle` to run the current
`examples/phase-3` subset.

The important constraint is that resumptive handlers cannot be implemented as
plain direct JavaScript calls plus thrown exceptions without losing the
continuation at the operation call site. The first design slice should decide
the executable representation for effectful computations, likely by compiling
effectful bodies to thunks or continuation-passing runtime calls while leaving
pure Phase 1 through Phase 2.6 code on the existing direct expression path.

The first implementation target should be handled `Raise`, because it proves
operation request creation, handler dispatch, handler `return`, and runtime
diagnostics without requiring `resume`. The second target should be resumptive
`Choose`, because it proves the continuation representation instead of only the
non-resuming handler path.

Keep unsupported diagnostics for accepted Phase 3 constructs outside the
supported runtime subset. A program that passes `fx check` but cannot yet be
emitted should fail during compile with a compiler diagnostic, not parser or
checker diagnostics.

## Scope

Include:

- JavaScript runtime support for operation requests, handler dispatch,
  ordinary returns, and explicit `resume`;
- compiler IR and lowering for operation calls, handler expressions,
  operation clauses, handler `return` clauses, and resume calls;
- JavaScript emission for the supported ordinary Phase 3 effect subset;
- executable Node smoke tests for handled `Raise` and resumptive `Choose`;
- regression coverage proving pure Phase 1, Phase 2, Phase 2.5, and Phase 2.6
  programs keep compiling and running;
- compiler diagnostics for checked effectful constructs that remain outside
  the Phase 3.1 executable subset.

Defer:

- scoped effects and named scopes;
- coeffects and `given`;
- effect masking;
- handler literals unless they become the simplest internal lowering target;
- multi-shot laws or restrictions beyond the runtime behavior needed for the
  supported examples;
- production packaging, bundling, source maps, optimization, and non-JavaScript
  targets;
- broad rewrites of the pure JavaScript backend.

## Work units

### 1. Runtime protocol design note and fixtures

Write down the JavaScript runtime protocol before changing lowering. The note
should define:

- how an operation request identifies the operation and carries payload values;
- how handlers match operation requests;
- how ordinary action returns reach the handler `return` clause;
- how `resume(value)` re-enters the suspended continuation;
- what happens when an operation escapes all handlers;
- whether supported resumptions are one-shot, multi-shot, or deliberately
  unspecified for Phase 3.1.

Acceptance:

- The protocol is concrete enough to implement in `crates/fx-compiler/src/runtime.rs`.
- It explains why the representation can support `Choose` without changing
  Phase 3 checker semantics.
- It states the unsupported subset and expected compiler diagnostic shape.

### 2. Add runtime helpers with direct Node tests

Extend the embedded JavaScript runtime with protocol helpers independent of
the compiler emitter.

Acceptance:

- Runtime tests cover constructing an operation request, handling a request,
  running a handler `return` clause, resuming a continuation, and reporting an
  unhandled operation.
- Existing variant, list, equality, and namespace isolation runtime tests keep
  passing.
- The runtime API stays under the `__fx` namespace.

### 3. Extend core IR for effectful control

Add explicit IR nodes for operation calls and handler expressions instead of
encoding them as ordinary calls.

Expected IR additions:

- operation call with resolved operation identity and lowered payload
  arguments;
- handler expression with lowered action, operation clauses, and return clause;
- clause payload parameters and explicit resume parameter;
- a way to identify calls to the synthetic resume parameter during emission.

Acceptance:

- Existing pure IR stays unchanged for pure programs.
- `CoreProgram::debug_tree()` exposes enough effect structure to debug lowered
  Phase 3 examples.
- Lowering still reports `unsupported-effect-runtime` for effect constructs not
  yet represented in IR.

### 4. Lower handled `Raise`

Lower the minimal non-resuming handler subset needed by `examples/phase-3`
`Raise` fixtures.

Acceptance:

- `handle action()` lowers the action, matching `raise` clause, and `return`
  clause.
- Operation calls resolve to operation IR, not ordinary global calls.
- Handler clauses can ignore `_resume` while returning a replacement value.
- Checked-but-unsupported effect constructs continue to fail before emission
  with compiler diagnostics.

### 5. Emit and smoke-test handled `Raise`

Emit JavaScript for the non-resuming subset and add Node smoke coverage.

Acceptance:

- A compact generated smoke test for `Raise` returns the fallback value.
- `fx compile --target js examples/phase-3` no longer fails solely because the
  `Raise` handler subset is present.
- Existing generated smoke tests for pure examples still pass.
- An unhandled operation in a compiled program produces a clear runtime error
  or compile-time unsupported diagnostic, according to the protocol note.

### 6. Lower explicit `resume`

Extend lowering for handler clause resume parameters and `resume(value)` calls.

Acceptance:

- The resume parameter is distinct from ordinary local functions in IR where
  needed for correct emission.
- `resume(value)` is lowered with the operation result type and handler result
  continuation shape established by Phase 3 checking.
- Non-resume ordinary calls remain emitted by the existing pure call path.

### 7. Emit and smoke-test resumptive `Choose`

Emit JavaScript for the resumptive subset and add the required Node smoke test.

Acceptance:

- `examples/phase-3/resume.fx` compiles and running `main()` returns `11`.
- A second smoke fixture can prove choosing the right branch if the runtime
  protocol makes that cheap.
- The test exercises the continuation around the operation call, not just a
  direct function callback.

### 8. Tighten unsupported diagnostics

Audit accepted Phase 3 constructs and make compile-time unsupported behavior
intentional.

Acceptance:

- Unsupported accepted constructs fail during `fx compile --target js` with
  `unsupported-effect-runtime`.
- Diagnostics are distinct from parser/checker diagnostics and point at the
  unsupported source construct.
- Supported `Raise` and `Choose` fixtures do not trigger the gate.

### 9. Preserve pure backend behavior

Run and, if needed, extend regression coverage around the existing direct
JavaScript backend.

Acceptance:

- Pure Phase 1, Phase 2, Phase 2.5, and Phase 2.6 fixtures still compile and
  run under Node.
- Pure code remains emitted in the existing compact direct style unless it is
  nested inside an effectful continuation that requires the new protocol.
- Cross-module imports and exported names remain stable.

### 10. Final Phase 3.1 validation and learnings

Update the Phase 3 learnings or create a Phase 3.1 learnings note with the
settled runtime decisions and validation evidence.

Acceptance:

- The final sweep includes formatting, compile-time tests, runtime helper
  tests, generated Node smoke tests, and CLI compile checks for examples.
- The learnings note records the runtime representation decision, unsupported
  subset, and any constraints on resumptions.
- Phase 3.1 completion criteria in
  `notes/2026-05-23-implementation-phases.md` are satisfied.
