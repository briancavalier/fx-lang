# Phase 3.5 learnings

Date: 2026-06-10

## Purpose

This note records implementation learnings and decisions from Phase 3.5 of the
implementation plan in `notes/2026-05-23-implementation-phases.md`.

Use it for formatter infrastructure decisions, comment/trivia preservation
limits, CLI behavior, golden fixture strategy, and verification evidence.

## Entries

- Decision: Expose a public syntax-token stream with comments and trivia while
  keeping parser-facing tokens filtered.
- Context: The parser previously skipped `#` comments and ordinary whitespace,
  which made a formatter API impossible to build without re-lexing source in a
  separate path. `fx_syntax::lex_source` now returns `SyntaxToken`s for
  comments, whitespace, newlines, indents, dedents, and ordinary lexical
  tokens. `parse_file` still consumes a filtered stream so existing parser
  behavior remains stable.
- Applies to phase(s): Phase 3.5.
- Future implication: Formatter work should use the public syntax-token stream
  plus AST spans instead of relying on the AST alone.
- Revisit when: Comments need deeper attachment semantics than leading,
  trailing, and block-local preservation.

- Decision: Start the formatter with a conservative API skeleton that validates
  by parsing and only normalizes file-level whitespace.
- Context: `fx_syntax::formatter::format_module` returns formatted source and a
  changed flag on success, or parser diagnostics on failure. The first
  implementation trims trailing spaces/tabs, collapses repeated blank lines,
  preserves comments as source text, ensures a final newline, and is
  idempotent.
- Applies to phase(s): Phase 3.5.
- Future implication: Broad formatting rules for declarations, types,
  expressions, handlers, and comments can grow behind the same API without
  changing CLI integration.
- Revisit when: The formatter begins reconstructing syntax from AST nodes and
  needs richer comment attachment.

- Decision: Add `fx fmt` and `fx fmt --check` early, even while the formatter
  style surface is still narrow.
- Context: The CLI now formats a single file or every `.fx` file under a
  directory in deterministic path order. Check mode reports files that would
  change and never writes. Malformed files report parser diagnostics and are
  not overwritten.
- Applies to phase(s): Phase 3.5.
- Future implication: Future formatter rules automatically become exercisable
  through the real command, and `fx fmt --check examples` can remain the
  phase-level validation gate.
- Revisit when: The CLI needs diff output, multiple explicit paths, or
  formatter configuration.

- Decision: Treat the current accepted examples as already canonical for the
  initial whitespace-only formatter.
- Context: `cargo run -p fx-cli -- fmt --check examples` reports all 14 example
  files formatted after the initial formatter slice. This does not yet prove
  full Phase 3.5 formatting rules, only the current skeleton behavior.
- Applies to phase(s): Phase 3.5.
- Future implication: As syntax-aware rules land, examples should either stay
  canonical or be intentionally reformatted once and then guarded by
  `fx fmt --check examples`.
- Revisit when: Golden fixtures for declarations, types, expressions, effects,
  and handlers are added.

- Decision: Reconstruct comment-free items from AST and preserve comment-bearing
  items from source until deeper comment attachment exists.
- Context: The formatter now canonicalizes imports, type declarations, effect
  declarations, value signatures, types, blocks, expressions, patterns, match
  arms, prefix `with`, handlers, and handler clauses. If a comment token falls
  inside a top-level item span, the formatter normalizes only file-level
  whitespace for that item instead of reconstructing it. This preserves comments
  inside blocks, match arms, handler clauses, and trailing item comments without
  pretending the formatter has a full attachment model.
- Applies to phase(s): Phase 3.5.
- Future implication: The next refinement can attach comments to statements,
  arms, clauses, fields, and cases incrementally while keeping the same public
  formatter API.
- Revisit when: Comment-bearing items should also receive full syntax-aware
  reformatting instead of source-preserving fallback.

- Decision: Canonical examples are formatted by `fx fmt` and guarded by
  `fx fmt --check examples`.
- Context: After syntax-aware declaration, type, expression, and handler
  formatting landed, the accepted examples were reformatted once. The examples
  now act as broad Phase 1 through Phase 3 formatting fixtures in addition to
  focused unit tests for compact messy inputs.
- Applies to phase(s): Phase 3.5.
- Future implication: Any future syntax formatting change that affects examples
  should be intentional and followed by the same check gate plus semantic tests.
- Revisit when: Separate golden fixture files are introduced for cases that do
  not belong in accepted examples.

- Decision: Sort only semantically conservative import groups.
- Context: `fx fmt` now sorts contiguous import groups only when there are no
  attached/interleaved comments and each imported module has a unique basename.
  Duplicate basenames are left in source order because qualified shorthand
  resolution chooses the first imported module whose basename matches.
- Applies to phase(s): Phase 3.5.
- Future implication: Import sorting remains safe under current resolver
  semantics while still cleaning up ordinary import groups.
- Revisit when: Import aliases, selective imports, or unambiguous qualified
  import resolution are added.
