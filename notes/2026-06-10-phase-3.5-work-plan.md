# Phase 3.5 work plan

Date: 2026-06-10

## Purpose

This note breaks Phase 3.5 from
`notes/2026-05-23-implementation-phases.md` into implementation units. Phase
3.5 adds opinionated formatter tooling after ordinary effects and the
JavaScript effects runtime have landed, but before scoped effects, coeffects,
and `given` add more surface area.

The formatter should be deliberate infrastructure, not a lossy AST
pretty-printer. It must preserve comments, produce stable output, report
diagnostics without overwriting malformed files, and be idempotent.

## Current fit

The current syntax layer has the right parser and AST spans to anchor a
formatter, but it is not sufficient by itself:

- `ParsedModule` keeps the original source and AST spans.
- The lexer currently skips `#` comments instead of exposing them.
- Whitespace and comments are not attached to AST nodes.
- There is no syntax-tree or token stream API intended for tooling consumers.
- The CLI already has file and directory collection patterns for `check` and
  `compile`, but it has no command that rewrites source.

The first implementation slice should therefore expose source trivia in the
syntax layer and establish the formatter contract before writing broad
formatting rules.

## Scope

Include:

- comment and source-trivia support needed by formatting;
- formatter API in the syntax/tooling layer;
- canonical formatting rules for Phase 1 through Phase 3 syntax;
- `fx fmt` for one file or every `.fx` file under a directory;
- `fx fmt --check` for CI and example validation;
- golden fixture tests for accepted Phase 1 through Phase 3 syntax;
- idempotence tests that formatting canonical output makes no changes;
- malformed-file behavior that reports diagnostics and does not overwrite
  source.

Defer:

- semantic refactors and code actions;
- aggressive import sorting that could change module resolution behavior;
- scoped effects, coeffects, and `given`;
- preserving arbitrary unusual spacing exactly as written;
- style configuration files or user-configurable formatter rules;
- LSP formatting integration unless it falls out cheaply after the API lands.

## Formatting contract

The Phase 3.5 formatter should use these rules unless implementation reveals a
better local convention:

- two-space indentation;
- one blank line between top-level declarations;
- one blank line between handler clauses and match arms only when their bodies
  are multi-line or when comments require separation;
- no trailing whitespace;
- final newline at end of file;
- commas and spaces normalized in records, variants, lists, tuples, calls,
  parameters, effect rows, and imports;
- row tails remain final and are printed as `...r`;
- effect rows are printed as `a with <Effect, ...e>`;
- function types keep result effects on the result side,
  `() -> a with <Effect>`;
- pipelines are vertically aligned as one expression per line when already
  multi-line or too complex for a compact single line;
- prefix `with` uses one target per line when there are multiple targets;
- `handle` clauses and `match` arms use the existing `name(args) ->` and
  `pattern ->` forms with indented multi-line bodies.

Comments should stay near the syntax they describe. The initial preservation
rule can be simple:

- full-line comments before an item, statement, clause, arm, field, or case
  stay before that construct at the same relative indentation;
- trailing comments stay on the formatted line when the line remains single
  line;
- comments inside malformed regions are not reformatted if parsing fails.

## Work units

### 1. Trivia model and lexer support

Expose comments and source trivia from `fx-syntax` without breaking existing
parser behavior.

Expected changes:

- add a public or crate-visible lexical token stream suitable for tooling;
- represent line comments, whitespace, newlines, indents, and dedents with
  spans;
- keep `parse_file` behavior stable for existing parser users;
- preserve current diagnostics for invalid characters, indentation, strings,
  and numeric literals.

Acceptance:

- Syntax tests prove `#` comments are visible to formatter tooling.
- Existing parser, core, compiler, CLI, and LSP tests still pass.
- Token/trivia spans slice back to the original source.
- Empty lines and indentation around comments can be reconstructed.

### 2. Formatter API skeleton

Add a formatter entry point in the syntax/tooling layer before implementing the
full style.

Expected API shape:

- `format_module(source: &str) -> FormatResult` or equivalent;
- success returns the formatted source and whether it changed;
- parse or lex diagnostics are returned without formatted output;
- the API is independent of CLI file-system concerns.

Acceptance:

- Unit tests cover unchanged already-canonical source and changed compact
  source.
- Malformed source returns diagnostics and does not produce replacement text.
- The API is exported from `fx-syntax` or a narrowly scoped formatter module
  that the CLI can call.
- Formatting the formatted result is byte-for-byte identical.

### 3. Top-level declarations, imports, and blank lines

Format module structure and top-level declarations.

Cover:

- `import` declarations;
- `export type`;
- `export effect`;
- value declarations and function parameters;
- top-level blank-line policy;
- leading and trailing top-level comments.

Acceptance:

- Golden fixtures cover compact and messy top-level modules.
- Comments before declarations are preserved.
- `export` placement is stable.
- Imports are normalized in place, and contiguous comment-free import groups
  are sorted only when imported module basenames are unique.

### 4. Type formatter

Format all accepted type syntax through Phase 3.

Cover:

- named and qualified types;
- type applications;
- function types;
- tuples;
- records and open record rows;
- variants and open variant rows;
- effect rows and open effect rows;
- operation signature result types.

Acceptance:

- Golden fixtures include Phase 2 rows and Phase 3 effect rows.
- Row tails are final in formatted output.
- Function result effects format as `() -> a with <Effect, ...e>`.
- Formatter output parses without diagnostics.

### 5. Expression formatter for Phase 1 through Phase 2.6

Format the pure expression surface before effect handlers.

Cover:

- literals, names, lists, records, record updates, fields, and calls;
- local bindings and block expressions;
- lambdas;
- `if`;
- `match`;
- patterns;
- binary operators;
- pipelines;
- prefix `with` trailing-action sugar.

Acceptance:

- Golden fixtures cover existing `examples/phase-1`, `examples/phase-2`,
  `examples/phase-2.5`, and `examples/phase-2.6`.
- Multi-line block formatting preserves statement order.
- Pipelines and prefix `with` are stable and readable.
- Formatting already formatted pure examples is idempotent.

### 6. Effect declaration and handler formatter

Format the Phase 3 effect surface.

Cover:

- `effect` declarations and operation signatures;
- operation calls as ordinary calls;
- `handle action()` expressions;
- operation clauses with explicit resume parameters;
- `return(value) ->` clauses;
- handler clause bodies;
- effect-polymorphic helper annotations.

Acceptance:

- Golden fixtures cover `examples/phase-3/effects.fx`,
  `examples/phase-3/imported.fx`, and `examples/phase-3/resume.fx`.
- Handler clause comments are preserved.
- `return` clauses stay visually distinct from operation clauses.
- Formatting Phase 3 examples is idempotent.

### 7. Comment attachment and preservation sweep

Tighten comment placement after the main formatter rules exist.

Acceptance:

- Fixture tests include leading file comments, comments between imports,
  comments before top-level items, comments inside blocks, comments before
  match arms, comments before handler clauses, and trailing comments.
- No accepted fixture loses comment text.
- The formatter does not invent blank lines that separate comments from the
  construct they describe.
- The preservation model is documented in this note or a Phase 3.5 learnings
  note.

### 8. `fx fmt` command

Add the CLI command that formats one file or every `.fx` file under a
directory.

Behavior:

- `fx fmt path/to/file.fx` formats that file in place;
- `fx fmt examples` formats every `.fx` file under `examples`;
- files are processed in deterministic path order;
- malformed files report diagnostics and are not overwritten;
- successful output reports changed and unchanged counts.

Acceptance:

- CLI tests cover single-file formatting, directory formatting, no-op
  formatting, malformed-file failure, and deterministic output order where
  observable.
- Existing `parse`, `symbols`, `check`, and `compile` commands keep their
  behavior.
- Usage text includes `fx fmt [--check] <root-or-file>`.

### 9. `fx fmt --check`

Add CI-friendly check mode.

Behavior:

- `fx fmt --check path` exits successfully when every target is already
  formatted;
- exits with failure when any target would change;
- prints the paths that need formatting;
- reports parse diagnostics for malformed files;
- never overwrites files.

Acceptance:

- CLI tests cover success, would-change failure, and malformed failure.
- `fx fmt --check examples` succeeds after examples have canonical formatting.
- The command is suitable for future CI use without additional flags.

### 10. Final validation and learnings

Complete the phase with a validation sweep and durable notes.

Acceptance:

- `cargo test` or the narrowest reliable equivalent passes.
- `fx fmt --check examples` succeeds.
- Golden fixtures cover Phase 1 through Phase 3 syntax.
- Idempotence tests cover every golden fixture.
- A Phase 3.5 learnings note records the trivia model, comment attachment
  limits, formatter API shape, and any deferred formatting decisions.
- Phase 3.5 success criteria in
  `notes/2026-05-23-implementation-phases.md` are satisfied.
