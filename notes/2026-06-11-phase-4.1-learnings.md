# Phase 4.1 learnings

Date: 2026-06-11

## Purpose

This note records implementation learnings and decisions from Phase 4.1 of the
implementation plan in `notes/2026-05-23-implementation-phases.md`.

`notes/2026-06-11-phase-4.1-work-plan.md`; the research context is

## Entries

- Decision: Implement Phase 4.1 as scoped metadata on ordinary effect
  requests.
- Context: Phase 3.1 already has a computation protocol for operation
  requests, handlers, returns, and resumptions. Phase 4.1 should extend that
  protocol with effect family and scope identity metadata rather than adding a
  separate scoped-effect runtime. `within` remains compile-time elaboration,
  and handlers must match exact family/scope instances while forwarding other
  requests.
- Applies to phase(s): Phase 4.1.
- Future implication: Fresh scopes, masking, and non-escape checks can add
  stronger identity and lifetime rules later without changing the v0 request
  shape.
- Revisit when: Phase 4.1 needs to support higher-order scoped operations,
  dynamic masking, or locally generated scopes.

- Decision: Preserve scoped operation metadata in compiler IR rather than
  reconstructing it in the JavaScript emitter.
- Context: Resolver references identify operation symbols but not their parent
  effect family, and checker-inserted `within` scope arguments are not stored
  as source AST call arguments. Lowering now recovers operation family metadata
  from parsed effect declarations, maintains a lexical default-scope stack for
  `within`, materializes checker-accepted elided scope arguments for ordinary
  function calls, and represents scoped requests as operation plus optional
  family and scope metadata. Scope metadata is not part of the operation
  payload.
- Applies to phase(s): Phase 4.1.
- Future implication: Later compiler work can inspect core IR to distinguish
  ordinary operation payloads from scoped dispatch metadata without parsing
  generated JavaScript.
- Revisit when: The checker exposes a richer typed core or persisted
  elaboration data for synthetic arguments.

- Decision: Treat `within` as a default scope provider for all function-like
  calls, not only effect operations.
- Context: The checker already accepts a call with one missing scope-compatible
  parameter inside `within`, including helper calls such as `with-state(0)`.
  Compiler lowering now mirrors that rule by inserting the active scope before
  emitted call arguments whenever checked function arity indicates one elided
  parameter. Scoped operations use the same materialized argument and then move
  it into request metadata.
- Applies to phase(s): Phase 4.1.
- Future implication: Helper APIs can be written scope-polymorphically without
  forcing call sites to repeat the active scope value inside a `within` block.
- Revisit when: The language adds multiple active default scopes with explicit
  priorities or scope masking.

- Decision: Lower top-level scopes as stable JavaScript identity values.
- Context: `scope Counter` now emits a frozen module-level object with a stable
  key such as `state.Counter`. Concrete scoped calls use that object directly,
  and scope-polymorphic helpers pass scope identities as ordinary runtime
  values. Protocol rows remain checker metadata and are not reauthorized by the
  runtime in Phase 4.1.
- Applies to phase(s): Phase 4.1.
- Future implication: Cross-module scopes can use the same generated import
  path as ordinary values, while diagnostics can print the stable key.
- Revisit when: Fresh scopes or capability authorization require runtime
  allocation or protocol checks.

- Decision: Infer scoped handler dispatch from the handled action function
  type when available.
- Context: Inferring a handler's scope from the action expression's remaining
  effects can choose the wrong scope when the action performs both the handled
  scope and another same-family scope. For handlers such as
  `with-state(cell, initial, action)`, the action parameter type states the
  owned `State s a` member. Lowering now prefers that function result type,
  maps the scope type to the runtime `cell` value, and emits handler entries
  that match family plus scope before operation clause dispatch.
- Applies to phase(s): Phase 4.1.
- Future implication: Handler helpers remain scope-polymorphic without
  monomorphization.
- Revisit when: Handler syntax grows first-class handler names or multiple
  handled effects per handler.

- Decision: Keep the existing Phase 3.1 resumption law for scoped handlers.
- Context: Scoped handler clauses still receive payload parameters plus
  `resume`. The JavaScript runtime re-enters the local handler when resuming
  and does not enforce linear use. Generated smoke tests cover concrete scoped
  calls, `within` elision, same-family different-scope forwarding, and a
  scope-polymorphic helper instantiated with a concrete scope.
- Applies to phase(s): Phase 4.1.
- Future implication: Scoped effects do not introduce branch-local state
  cloning or one-shot continuation restrictions.
- Revisit when: The language chooses explicit one-shot, linear, or multi-shot
  resumption laws.

- Decision: Keep public Phase 4 examples runnable when they demonstrate the
  supported runtime subset.
- Context: `examples/phase-4/polymorphic.fx` now includes a concrete
  `main()` that runs a scope-polymorphic `increment(cell)` helper through
  `within Counter` and `with-state(10)`. The example still keeps effectful
  exported helpers for checker-facing scope-polymorphism examples, but users
  can compile the file to an output directory and run the generated module
  directly with Node.
- Applies to phase(s): Phase 4.1.
- Future implication: Later examples should distinguish runnable demonstrations
  from intentionally effectful API examples.
- Revisit when: The example runner or package format changes how generated
  modules expose entry points.
