# Phase 4.1 scoped effect runtime research

Date: 2026-06-11

## Purpose

This note records the research needed to start Phase 4.1 from
`notes/2026-05-23-implementation-phases.md`.

Phase 4.1 should make checked Phase 4 scoped-effect programs executable by the
JavaScript compiler and runtime. Phase 4 already established syntax, checking,
diagnostics, `within` elaboration, scoped handler typing, and compile-time
runtime gating. This note focuses on the compiler/runtime design questions that
must be settled before removing that gate.

## Local baseline at start

Phase 3.1 represents effectful JavaScript as explicit runtime computations. The
runtime provides `__fx.effect`, `__fx.pure`, `__fx.perform`, `__fx.bind`,
`__fx.handle`, and `__fx.run`. Pure expressions still emit direct JavaScript;
operation calls, handlers, and calls to effectful helpers use the computation
emitter.

Today, `__fx.perform(operation, payload)` creates requests with:

- an operation key;
- a payload array;
- a `resume` continuation.

`__fx.handle(action, spec)` looks up a clause by `request.operation`. Unknown
requests are forwarded to the outer handler. Resuming re-enters the local
handler, so nested or repeated operations after a resume are interpreted by the
same handler.

Phase 4 currently blocks execution in the compiler:

- `scoped effect` declarations report that scoped effect declarations are not
  executable yet;
- `scope` declarations report that scope declarations are not executable yet;
- `within` expressions report `unsupported scoped-effect runtime`;
- accepted scoped-effect programs still check successfully.

The static Phase 4 decisions that matter most for 4.1 are:

- `within` stores the resolved scope type, not only a source name;
- elided scoped calls are resolved by the checker and should be treated as
  explicit scoped calls by runtime lowering;
- scoped handler clauses omit the implicit scope slot from payload parameters;
- handler checking removes exactly one structured effect member, such as
  `State Counter Int`, and leaves same-family effects at other scopes
  unhandled;
- Phase 4 intentionally defers fresh scopes, masking, first-class handler
  names, non-escape checking, multiple protocol rows, coeffects, and protocol
  authorization beyond static validation.

## Implemented Phase 4.1 result

Phase 4.1 implemented the conservative design from this research note. Scoped
requests are now ordinary effect requests with optional family and scope
metadata. Scope declarations lower to frozen JavaScript identity objects with
stable diagnostic keys. `within` remains compile-time elaboration and supplies
the active scope value to effect operations and other function-like calls whose
scope-valued parameter is elided.

The compiler/runtime subset now supports:

- top-level `scope` declarations, including exported scopes;
- explicit scoped operation calls such as `get(Counter)`;
- elided calls inside `within Counter` or `within cell`;
- scoped handler dispatch by exact family plus scope identity;
- payload-only scoped handler clauses;
- scope-polymorphic helpers that receive scope identities as runtime values;
- unhandled scoped diagnostics that include scope information.

Phase 4.1 still intentionally defers fresh scopes, non-escape checking, scope
masking, first-class handler names, multiple protocol-row entries per scope,
coeffects and `given`, runtime protocol authorization, and any change to the
Phase 3.1 resumption law.

## External research summary

### Formal scoped and higher-order effects

Research on scoped effects distinguishes two ideas that are easy to conflate:

- algebraic operations indexed by an extra name, region, or resource identity;
- higher-order scoped operations that delimit or contain a subcomputation.

`Structured Handling of Scoped Effects` is useful because it compares multiple
ways to model scoped operations, including translations through algebraic
operations. The main lesson for Phase 4.1 is conservative: fxl's v0 named
scopes do not need full higher-order scoped operations. `State Counter Int`
can compile as an ordinary algebraic request indexed by stable scope identity.

`A Framework for Higher-Order Effects & Handlers` and `Scoped Effects as
Parameterized Algebraic Theories` are useful background for later fresh-scope,
masking, bracketing, and non-escape work. They should not drive Phase 4.1 into
supporting operations that capture subcomputations.

Research links:

- https://arxiv.org/abs/2201.10287
- https://arxiv.org/abs/2302.01415
- https://arxiv.org/abs/2402.03103

### Koka

Koka is the closest practical reference for row-polymorphic effects, handlers,
masking, isolated state, resumptions, and named/scoped handler ideas. Its book
also documents masking and named/scoped handlers as distinct advanced features.

The useful lesson is that named/scoped behavior should be separated from
masking. Phase 4.1 should not make scope identity double as an effect-masking
mechanism. A handler either matches the exact scoped request key or forwards the
request outward.

Reference:

- https://koka-lang.github.io/koka/doc/book.html

### Frank and Unison

Frank and Unison both reinforce that effect availability should be explained in
terms of handlers and ability requirements rather than unifier internals.
Unison's ability handlers expose requests explicitly and permit handlers to
resume, ignore, or resume multiple times.

The useful lesson for fxl is diagnostic and runtime-shape oriented: request
objects are a good mental model. A scoped request should remain a request with
extra identity, not an unrelated runtime path.

References:

- https://arxiv.org/abs/1611.09259
- https://www.unison-lang.org/docs/language-reference/abilities-and-ability-handlers/

### OCaml 5

OCaml 5 exposes effect handlers through delimited continuations and uses
one-shot continuations. The relevant warning is that resumption laws affect
resource and state semantics. fxl's current JavaScript runtime does not enforce
one-shot continuations and already permits multi-shot-style handler code.

Phase 4.1 should document that scoped state in v0 follows the existing Phase
3.1 resumption behavior. If fxl later chooses linear or one-shot resumptions,
that should be a separate runtime-law decision rather than hidden inside scoped
effects.

Reference:

- https://ocaml.org/manual/5.2/effects.html

## Coherent Phase 4.1 design direction

### Treat scoped requests as indexed ordinary requests

Do not add a separate runtime construct for scoped effects. Extend operation
requests so they can carry optional scoped metadata:

- operation identity;
- effect family identity;
- scope identity;
- payload.

Ordinary Phase 3 operations can continue to use the existing operation-only
path. Scoped Phase 4 operations should use the same computation protocol with
extra matching information.

The expected runtime shape is conceptually:

```js
__fx.performScoped("main.State.get", "main.State", __fx_scope_Counter, [])
```

or a generalized:

```js
__fx.perform({ operation, family, scope, payload })
```

The second shape is cleaner long-term because it avoids parallel request
constructors, but it must preserve source compatibility for generated ordinary
operations.

### Lower scope declarations to stable identities

Each top-level `scope Name` declaration should lower to a stable module-level
JavaScript identity. A frozen object is sufficient for v0:

```js
const __fx_scope_Counter = Object.freeze({
  __fx_scope: true,
  key: "main.Counter",
});
```

The runtime should compare scopes by object identity or stable key, but the
compiler should pick one rule and use it everywhere. Object identity is simpler
inside one generated module graph. Stable keys make diagnostics and cross-module
imports easier. A hybrid frozen object with a stable key gives both.

Scope declarations are values for code generation purposes. Scope-polymorphic
helpers such as `increment(cell: s)` should receive a scope identity at runtime
and pass it to scoped operations. There is no need for monomorphization in
Phase 4.1.

### Keep `within` compile-time only

`within` should not produce a runtime dynamic-scope lookup. The checker has
already resolved elided calls and recorded typed spans. Compiler lowering
should either:

- lower the checker's synthetic first scope argument if it is already preserved
  in the checked AST/analysis; or
- reconstruct the same explicit scope argument from checked call metadata.

The runtime should only see explicit scoped operation requests. If the compiler
cannot currently access the synthetic scoped argument for `get()` inside
`within`, that is the first IR gap to close.

### Match handlers by scoped operation/family/scope

For ordinary effects, handler specs can remain keyed by operation.

For scoped effects, handler specs need enough information to handle only the
target family/scope pair. There are two plausible matching levels:

1. Key each clause by operation plus scope.
2. Key the handler by family plus scope, then key clauses by operation within
   that family.

The second matches the type checker more closely. A `with-state(Counter, ...)`
handler handles the `State` family at `Counter`; its `get` and `put` clauses are
operation clauses inside that handled family/scope instance.

Recommended v0 runtime shape:

```js
__fx.handle(action, {
  handlers: [
    {
      family: "main.State",
      scope: cell,
      operations: {
        "main.State.get": (resume) => ...,
        "main.State.put": (value, resume) => ...,
      },
    },
  ],
  return: (value) => __fx.pure(value),
})
```

This keeps ordinary operation-only handlers compatible while making scoped
dispatch explicit. A request whose family matches but scope differs must be
forwarded to the outer handler.

### Preserve payload-only handler clauses

Phase 4 checker behavior intentionally hides the implicit scope slot from
handler clause parameters. Runtime lowering should do the same: the scope is
dispatch metadata, not a payload argument.

For:

```fx
put(Counter, n + 1)
```

the emitted request payload for the `put` clause should contain only `n + 1`.
The `Counter` identity should be stored in request metadata.

### Scope-polymorphic helpers are the main risk

Concrete scopes are straightforward: `Counter` lowers to a module-level scope
identity.

Scope-polymorphic helpers are the important validation case:

```fx
increment(cell: s) : Int with <State s Int>
  within cell
    n = get()
    put(n + 1)
    n
```

The compiler must emit a JavaScript function that accepts `cell` as a runtime
scope identity and emits scoped requests using that value. This means:

- scope variables do not disappear after type checking;
- scope-valued parameters need ordinary value lowering;
- elided calls inside `within cell` must lower as if written
  `get(cell)` and `put(cell, n + 1)`;
- handler helpers such as `with-state(cell, initial, action)` should compare
  requests against the runtime value passed as `cell`.

If this cannot be expressed in the current core IR, Phase 4.1 needs an IR slice
before runtime changes.

### Resumption and state semantics need an explicit v0 law

The existing JavaScript runtime permits handlers to call `resume` according to
ordinary JavaScript function behavior. It does not enforce linear use.

For Phase 4.1, scoped state examples should document the v0 law:

- handler-local state captured by a JavaScript closure is shared by all resumes
  through that handler;
- resuming re-enters the same local handler;
- multiple resumes are governed by the existing Phase 3.1 runtime behavior;
- no branch-local state cloning is introduced for scoped effects.

The current `examples/phase-4/state.fx` handler does not actually update state:
`put(_value, resume) -> resume(unit)`. Before using it as the executable state
smoke test, Phase 4.1 should either add a stateful handler example that mutates
handler-local JS state through lowered code, or rename the smoke target to make
clear it tests scope dispatch rather than mutable state.

## Compiler questions to answer before implementation

1. Does core lowering currently preserve the checker-inserted synthetic scope
   argument for elided scoped calls?
2. Can a scope declaration be represented as a core value declaration, or does
   the IR need a `CoreDecl::Scope`?
3. Should `CoreExprKind::Operation` grow optional `family` and `scope`
   fields, or should scoped operations get a separate `CoreExprKind` variant?
4. Does `operation_reference(span)` carry enough metadata to find the scoped
   effect family for a scoped operation?
5. Can handler lowering recover the handled scoped family/scope from checked
   action effects and clause operation metadata?
6. How should generated JS import scope identities across modules?
7. Should runtime unhandled diagnostics print just the operation key or the
   scoped effect member, such as `State OtherCounter Int`?

## Recommended implementation slices

1. Add compiler fixtures for the intended generated shape before editing the
   runtime.
2. Extend core IR for scope identities and scoped operation metadata.
3. Lower `scope` declarations to stable module-level identities.
4. Lower explicit scoped calls so request metadata carries family and scope
   while payload excludes the scope slot.
5. Lower `within` elision by consuming or reconstructing the checker-resolved
   explicit scope argument.
6. Extend runtime request dispatch for scoped family/scope matching while
   preserving ordinary operation dispatch.
7. Add generated Node smoke tests for:
   - concrete `State Counter Int`;
   - explicit scoped calls;
   - `within` elision;
   - same family with two scopes where one remains unhandled;
   - a scope-polymorphic helper instantiated with concrete scopes.
8. Remove scoped-effect unsupported diagnostics only for constructs covered by
   those tests.

## Non-goals for Phase 4.1

- fresh scope creation;
- non-escape checking;
- scope masking;
- first-class handler names;
- multiple protocol-row entries per scope;
- dynamic lookup for `within`;
- branch-local cloning of handler state;
- coeffects or `given`;
- changing ordinary Phase 3 effect runtime behavior.

## Recommendation

Proceed with Phase 4.1 as a runtime indexing extension to the existing Phase
3.1 computation protocol. The coherent v0 model is:

> A scoped effect request is an ordinary algebraic request plus family and
> scope identity metadata. `within` is compile-time elaboration. Handlers match
> exact family/scope instances and forward everything else.

This design is small enough to implement against the current compiler, preserves
the Phase 4 static semantics, and leaves the advanced scoped-effect literature
available for later fresh-scope, masking, and non-escape phases without
pretending those features already exist.
