# Phase 4.1 work plan

Date: 2026-06-11

## Purpose

This note breaks Phase 4.1 from
`notes/2026-05-23-implementation-phases.md` into implementation units. Phase
4.1 makes the checked Phase 4 scoped-effect subset executable through the
existing JavaScript compiler and runtime.

Phase 4 already accepts scoped effect declarations, scope declarations,
scope-polymorphic rows, explicit scoped operation calls, `within` elision,
scoped handler checking, diagnostics, LSP-adjacent metadata, and compiler
runtime gating. This phase should replace the scoped-effect runtime gate for a
small supported subset without reopening Phase 4 checker semantics.

The research context is in `notes/2026-06-11-phase-4.1-research.md`.

## Design target

Implement scoped effects as an indexing extension to the existing Phase 3.1
effect computation protocol:

> A scoped effect request is an ordinary algebraic request plus family and
> scope identity metadata. `within` is compile-time elaboration. Handlers match
> exact family/scope instances and forward everything else.

Phase 4.1 should preserve ordinary Phase 3 effect runtime behavior. It should
only remove unsupported diagnostics for scoped constructs that are represented
in IR, emitted to JavaScript, and covered by runtime smoke tests.

## Scope

Include:

- stable JavaScript identities for top-level `scope` declarations;
- core IR metadata for scoped operation requests;
- lowering for explicit scoped calls such as `get(Counter)`;
- lowering for checker-elaborated `within` calls such as `get()` inside
  `within Counter` or `within cell`;
- runtime request metadata for operation identity, effect family identity,
  scope identity, and payload;
- handler dispatch that matches scoped requests by family plus scope and then
  operation clause;
- payload-only scoped handler clauses, preserving the Phase 4 checker rule that
  the implicit scope slot is dispatch metadata rather than a clause parameter;
- generated JavaScript smoke tests for concrete scopes, `within` elision,
  explicit scoped calls, same-family different-scope forwarding, and
  scope-polymorphic helpers instantiated with concrete scopes;
- regression coverage proving ordinary Phase 3 effect programs and pure Phase
  1 through Phase 2.6 programs keep compiling and running.

Defer:

- fresh scope creation;
- non-escape checking;
- scope masking;
- first-class handler names;
- multiple protocol-row entries per scope;
- dynamic runtime lookup for `within`;
- branch-local cloning of handler state;
- coeffects and `given`;
- capability or protocol authorization beyond current checker validation;
- changing Phase 3.1 resumption laws.

## Work units

### 1. Phase 4.1 setup and learning log

Create the phase execution scaffolding before compiler edits.

Acceptance:

- `notes/2026-06-11-phase-4.1-learnings.md` exists with the established
  learning-log shape:
  - Decision:
  - Context:
  - Applies to phase(s):
  - Future implication:
  - Revisit when:
- The learnings note links back to this work plan and the Phase 4.1 research
  note.
- The initial entry records the v0 runtime model: scoped requests are indexed
  ordinary effect requests, `within` is compile-time elaboration, and exact
  family/scope matching is required.

### 2. Add focused Phase 4.1 runtime fixtures

Promote the runtime-relevant Phase 4 examples into smaller compiler smoke
fixtures before changing the runtime.

Acceptance:

- A concrete scoped fixture covers `State Counter Int` with a handler that
  returns a deterministic observable value.
- A fixture covers explicit scoped calls such as `get(Counter)`.
- A fixture covers `within Counter` elision.
- A fixture covers two scopes of the same family where handling
  `State Counter Int` leaves `State OtherCounter Int` unhandled.
- A fixture covers a scope-polymorphic helper such as `increment(cell)` called
  with `Counter`.
- Fixture names distinguish scope dispatch from mutable state unless a real
  stateful interpreter is added.

### 3. Audit checked scoped-call metadata available to lowering

Determine exactly what compiler lowering can see for explicit and elided
scoped operation calls.

Questions:

- Does the current checked AST or analysis preserve the synthetic first scope
  argument inserted for elided calls inside `within`?
- Does `operation_reference(span)` expose enough information to identify the
  scoped effect family for a scoped operation?
- Can lowering distinguish the scope argument from payload arguments without
  re-running checker resolution?
- Can handler lowering recover the handled family/scope pair from checked
  metadata?

Acceptance:

- The audit result is recorded in the Phase 4.1 learnings note.
- Any missing metadata is identified as an explicit IR/lowering task.
- No runtime unsupported diagnostic is removed in this slice.

### 4. Extend core IR for scopes and scoped requests

Represent scope identities and scoped operation metadata explicitly in core IR.

Expected IR additions:

- a way to represent top-level scope declarations as emitted module-level
  values;
- operation requests with optional scoped metadata: family identity and scope
  expression;
- handler clauses or handler specs with optional handled family/scope metadata;
- debug-tree output that makes scoped request metadata visible.

Acceptance:

- Pure programs produce the same IR shape as before.
- Ordinary Phase 3 operation requests still lower without scoped metadata.
- Scoped operation requests preserve operation identity, family identity, scope
  expression, and payload arguments separately.
- `CoreProgram::debug_tree()` or equivalent compiler tests can assert that the
  scope is metadata, not a payload argument.

### 5. Lower scope declarations to stable JavaScript identities

Lower each top-level `scope Name` declaration to a stable module-level runtime
identity.

Recommended emitted shape:

```js
const __fx_scope_Counter = Object.freeze({
  __fx_scope: true,
  key: "main.Counter",
});
```

Acceptance:

- Scope declarations no longer trigger the broad "scope declarations are not
  executable yet" gate when the rest of the module is inside the supported
  Phase 4.1 subset.
- Exported scopes can be imported by generated JavaScript for another module.
- Scope identity lowering works for bare scopes and scopes with protocol rows;
  protocol rows remain checker metadata and do not need runtime authorization
  in Phase 4.1.
- Scope identity names avoid collisions with user values and existing generated
  helper names.

### 6. Lower explicit scoped operation calls

Lower calls such as:

```fx
get(Counter)
put(Counter, n + 1)
```

into scoped operation requests.

Acceptance:

- The scope argument lowers to request metadata.
- Payload arguments exclude the scope argument.
- Operation identity and effect family identity are both available to the
  emitter.
- Existing ordinary operation calls lower exactly as before.
- Compiler tests assert the IR shape for `get(Counter)` and `put(Counter,
  value)`.

### 7. Lower `within` elision through checked scope metadata

Lower elided calls inside `within` as the same scoped request shape as explicit
calls.

Acceptance:

- `within Counter { get(); put(n + 1) }` emits requests using the `Counter`
  scope identity.
- `within cell` in a scope-polymorphic helper emits requests using the runtime
  value of the `cell` parameter.
- `within` itself does not emit dynamic runtime scope lookup.
- Unsupported diagnostics remain for any `within` shape whose checked scoped
  argument cannot yet be represented.

### 8. Extend JavaScript runtime request protocol

Extend the embedded runtime to carry optional scoped request metadata while
preserving ordinary operation behavior.

Acceptance:

- `__fx.perform` continues to support ordinary operation-key requests, or a
  compatibility wrapper preserves the generated Phase 3 call shape.
- Scoped requests carry operation, family, scope, payload, and resume.
- Runtime helper tests cover matching scoped metadata and forwarding
  non-matching requests outward.
- Existing runtime tests for variants, lists, equality, ordinary effects,
  ordinary handlers, resumes, and unhandled operations keep passing.

### 9. Emit scoped handler dispatch

Emit handler specs that match scoped requests by family plus scope, then by
operation clause.

Acceptance:

- A handler for `State Counter Int` handles `get` and `put` requests whose
  family is `State` and scope is `Counter`.
- The same handler forwards `State OtherCounter Int` requests outward.
- Scoped handler clauses receive only payload parameters plus `resume`.
- Handler `return` clauses behave as in Phase 3.1.
- Ordinary Phase 3 handler emission is unchanged or passes equivalent
  regression tests.

### 10. Smoke-test concrete scoped execution

Add generated Node smoke coverage for the smallest concrete scoped example.

Acceptance:

- A generated program with `scope Counter`, `get(Counter)`, a matching handler,
  and `main` runs under Node and prints or returns the expected value.
- The test exercises runtime request dispatch rather than only compile-time
  lowering.
- Existing pure and ordinary effect generated smoke tests keep passing.

### 11. Smoke-test `within` elision

Add generated Node smoke coverage proving `within` elision compiles to explicit
scoped requests.

Acceptance:

- A generated program using `within Counter` and elided `get()`/`put(...)`
  runs under Node with the same behavior as the explicit-call version.
- The generated JavaScript contains no dynamic `within` runtime mechanism.
- Hover/LSP behavior is not changed by compiler-only lowering work.

### 12. Smoke-test same-family different-scope forwarding

Add generated Node smoke coverage for exact scope matching.

Acceptance:

- A handler for `State Counter Int` does not handle `State OtherCounter Int`.
- The test observes the remaining request as either a compile-time unhandled
  effect when the source type is pure, or a runtime unhandled operation when
  deliberately run without an outer handler.
- The runtime diagnostic includes enough scope information to distinguish
  `Counter` from `OtherCounter`.

### 13. Smoke-test scope-polymorphic helpers

Add generated Node smoke coverage for helpers parameterized over a scope value.

Acceptance:

- A helper such as `increment(cell: s)` compiles to JavaScript that accepts a
  runtime scope identity.
- Calling the helper with `Counter` emits requests against `Counter`.
- The test proves the scope parameter is not erased after type checking.
- No monomorphization is required for Phase 4.1.

### 14. Tighten scoped unsupported diagnostics

Replace broad scoped-effect runtime gates with precise unsupported diagnostics.

Acceptance:

- Supported scoped declarations, explicit calls, `within` elision, and scoped
  handlers no longer report `unsupported scoped-effect runtime`.
- Unsupported accepted scoped constructs still fail during `fx compile
  --target js` with compiler diagnostics, not parser/checker diagnostics.
- Diagnostics point at the unsupported source construct.
- The gate remains for deferred features such as fresh scopes, masking, and
  multiple protocol rows if those syntactic forms later become accepted.

### 15. Preserve older executable phases

Run regression coverage across the existing executable surface.

Acceptance:

- Pure Phase 1, Phase 2, Phase 2.5, and Phase 2.6 examples still compile and
  run under Node.
- Ordinary Phase 3 effect examples still compile and run under Node.
- Runtime helper tests for ordinary effects still pass.
- JavaScript output for pure programs remains direct and compact unless nested
  inside an effectful computation path.

### 16. Final Phase 4.1 validation and documentation

Finish the phase with validation evidence and durable notes.

Acceptance:

- `fx compile --target js examples/phase-4/state.fx` succeeds for the supported
  subset or the example is split so the supported executable fixture is clear.
- Scope-polymorphic examples from `examples/phase-4/polymorphic.fx` compile
  when instantiated with concrete scopes covered by runtime support.
- The final sweep includes compiler tests, runtime helper tests, generated Node
  smoke tests, CLI compile checks, and CLI check regressions.
- `notes/2026-06-11-phase-4.1-learnings.md` records the settled runtime
  request shape, scope identity rule, handler dispatch rule, resumption/state
  law, unsupported subset, and validation evidence.
- Phase 4.1 completion criteria in
  `notes/2026-05-23-implementation-phases.md` are satisfied or explicitly
  narrowed with rationale.

## Suggested implementation order

1. Setup and learning log.
2. Runtime fixtures and metadata audit.
3. Core IR for scope identities and scoped request metadata.
4. Scope declaration lowering.
5. Explicit scoped call lowering.
6. `within` elision lowering.
7. Runtime request protocol extension.
8. Scoped handler dispatch emission.
9. Generated Node smoke tests for concrete, explicit, and elided calls.
10. Same-family different-scope forwarding.
11. Scope-polymorphic helper execution.
12. Unsupported diagnostic tightening.
13. Regression sweep for earlier executable phases.
14. Final learnings and validation evidence.

Keep each work unit small enough to validate with focused compiler/runtime tests
before broadening the supported scoped-effect subset.

## Completion status

Completed on 2026-06-12 for the Phase 4.1 v0 runtime subset:

- Work units 1-3 established the learning log, runtime smoke fixtures, and
  lowering metadata audit.
- Work units 4-7 added IR support for scope declarations and scoped requests,
  lowered top-level scope identities, lowered explicit scoped calls, and
  lowered `within` elision without a dynamic runtime lookup.
- Work units 8-9 extended the JavaScript runtime request protocol with
  `performScoped` and emitted scoped handler dispatch by exact family plus
  scope identity.
- Work units 10-13 added generated Node smoke coverage for concrete scoped
  execution, `within` elision, same-family different-scope forwarding,
  exported scope identities, and scope-polymorphic helpers.
- Work unit 14 removed the broad scoped runtime gates for the supported subset;
  unsupported accepted constructs remain compiler diagnostics.
- Work units 15-16 passed the broader regression sweep and recorded the settled
  runtime model in `notes/2026-06-11-phase-4.1-learnings.md`.

The runnable user-facing Phase 4 examples are:

- `examples/phase-4/state.fx`, where `handled-counter()` demonstrates concrete
  scoped state and exact handler dispatch;
- `examples/phase-4/polymorphic.fx`, where `main()` runs a scope-polymorphic
  `increment(cell)` helper with the concrete `Counter` scope.

Example commands:

```sh
cargo run -q -p fx-cli -- compile --target js --out-dir /tmp/fxl-phase-4-state examples/phase-4/state.fx
cargo run -q -p fx-cli -- compile --target js --out-dir /tmp/fxl-phase-4-polymorphic examples/phase-4/polymorphic.fx
node /tmp/fxl-phase-4-polymorphic/polymorphic.mjs
```

Deferred work remains Phase 4.2+ material: fresh scopes, lifetime/non-escape
rules, scope masking, richer protocol rows, first-class handler names,
coeffects/given integration, runtime authorization, and any revised resumption
law.
